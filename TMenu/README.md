# Building TMenu.exe

## Why you have to run this yourself
PyInstaller can't cross-compile — a Windows `.exe` has to be built *on Windows*.
This sandbox is Linux, so I fixed up the source and wrote the build script,
and verified the whole packaging pipeline builds and runs cleanly here as a
Linux binary — but you need to run `build.bat` on your own Windows machine to
get the actual `TMenu.exe`.

## Steps
1. Install Python 3.10+ on Windows if you don't have it (python.org, tick
   "Add to PATH" during install).
2. Copy this whole folder onto your Windows machine. If you want the exe to
   have a custom icon, drop an `icon.ico` file in here too (same folder as
   `build.bat`) - it's entirely optional, the build works fine without one.
3. Double-click **build.bat** (or open a command prompt in this folder and
   run `build.bat`). It'll ask for a version number first - type one (e.g.
   `15.2.0`) or just press Enter to reuse whatever version was used last time.
4. When it finishes, everything you hand out is in the new **dist\** folder:
   - `TMenu.exe` (the icon, if you supplied one, is compressed directly into
     this exe by the build - it's not shipped as a separate `.ico` file)
   - `settings.json`, `theme.json`, `challenge_keys.json`, `challenge_types.json`

   Keep those JSONs next to the exe — that's what "single file, jsons next
   to it" means here: the exe is the one compiled file, but the app still
   reads/writes those JSONs at runtime (settings, theme, challenge editor),
   so they live beside it on disk rather than being baked inside it.

   Anything you *export* from inside the running app (a theme, a challenge,
   a config, binds, a skater recipe) works differently: each EXPORT button
   opens a normal Save dialog that's already pointed at its own subfolder
   next to the exe - `theme\`, `challenge\`, `config\`, `binds\`, `recipes\`
   - creating that folder the first time you export that kind of thing, with
   a sensible filename already filled in that you can rename (or save
   somewhere else entirely) before confirming. IMPORT/LOAD buttons open in
   that same subfolder by default.

## What's baked into the exe
Right-click `TMenu.exe` → Properties → Details will show:
- **Company/Author:** TDG
- **File description:** A large multiuse RTM tool for Skate 3 on the PS3
- **Version:** whatever you typed in at the build.bat prompt (defaults to
  0.15.1.0 the very first time, before any version has been entered)

If an `icon.ico` sits next to `build.bat` when you build, that same icon is
compressed directly into the exe itself (Explorer, taskbar, shortcuts, etc.
all pick it up from there) - it isn't copied out as a loose file anywhere.

**Changing company/description/product name:** those don't change per build -
edit the constants at the top of `build_version.py` if you ever want to
change any of that, then rebuild. `version_info.txt` itself is now
auto-generated by `build_version.py` every time `build.bat` runs, so don't
hand-edit it directly - it'll just get overwritten on the next build.

**Changing the version without rebuilding right now:** `version.txt` holds
whatever version number was last used (just the plain number, nothing else) -
edit that file directly if you want to change the "remembered" default
without running a full build.

## What I changed in the source (and why)
The original code found `settings.json` / `theme.json` / `challenge*.json`
via each module's own `__file__`, which resolves to whatever folder that
`.py` file is sitting in. That's fine running from source, but once
PyInstaller bundles everything into one `.exe`, `__file__` for those modules
points into a temporary folder PyInstaller extracts itself into at startup —
a fresh throwaway location every single run, not the folder the exe lives
in. Settings, your theme, and challenge edits would silently stop saving
between runs.

Fix: added `app_paths.py`, a single shared `base_dir()` used everywhere
instead — it resolves to the real exe folder when frozen, and behaves exactly
like before when just running `python app.py`. Also made the (currently
unused/fallback) restart-helper code exe-aware, so relaunching after a
restart still works if that path ever gets exercised. Nothing about the
app's behavior, UI, or features changed — this only fixes where files are
looked for once compiled.

## Exports now save via a dialog, sorted into per-kind folders
Every EXPORT-style button (theme, challenge, config, binds, skater recipe)
used to either write straight to a fixed file next to the exe with no
prompt at all (challenge, theme's "New Default Theme.json"), or prompt with
a Save dialog but drop the result wherever the dialog last was (config,
binds, recipe). Both are now the same behavior everywhere: `app_paths.py`
gained `export_dir(kind)` / `export_save_path(...)`, which create a
`<kind>\` folder next to the exe on first use and open a Save dialog
already pointed at `<kind>\<default_filename>` - the user renames or
relocates from there if they want, nothing is written silently. The
matching IMPORT/LOAD buttons open in that same folder by default. See
`theme\`, `challenge\`, `config\`, `binds\`, `recipes\` after your first
export of each kind.

## Running from source instead (no compiling)
```
pip install -r requirements.txt
python app.py
```
